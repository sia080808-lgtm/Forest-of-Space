# APK1.1.6 · 렉 줄이기 2: 화면 한 장 그리는 비용

2026-11-21. 사용자 요청: "원래 이런 게임 돌리면 폰 자체가 좀 렉이 걸리나" → "일반 모바일 게임처럼 그래픽 칩에서 하면 되나" → 한 장 그리는 비용 줄이기 → "한장 그리는 비용줄이기 하면 퀄 낮아보일까" → "ㄱㄱ".

측정 방법: 실제 크롬 브라우저(그래픽 칩 없는 소프트웨어 그리기, 휴대폰 크기 393×690 · 화면 배율 2.5)에서 친구 6명·여름 호수 채움 장면을 그린다(`tools/render-bench.cjs`). 컴퓨터 Node 그림판은 필터·임시 그림판 비용이 브라우저와 크게 달라서(1.1.4까지의 측정 방식) 이번에는 브라우저로 쟀다.

찾은 원인과 변경 내용(그림·규칙 그대로, 렌더 전용):
- **떨어진 낙엽(`scene.js` `drawFallenLeaf`·`bakeLeaf`):** 낙엽 한 장마다 그림자를 흐림 필터(`blur`)로 매 장 다시 그렸다(한 장의 절반 이상). 낙엽 모양마다 그림자·종이 질감·겨울 흰빛·가을 물듦을 한 번 구워 두고 같은 변환으로 그린다. 낙엽 자리의 잎과 거름 조각도 같은 방식.
- **사물의 젖은 모습(`terrain`·`creviceFront`·`wetTile`):** 바위·바위틈·이끼·낙엽 자리는 흙이 촉촉하면(거의 늘) 밝기·채도 필터를 매 장 씌웠다. 젖은 정도(1/20 단위)마다 화면에 그려지는 크기로 필터를 입힌 그림을 미리 만들어 둔다. 마른 사물은 필터 없이 그린다.
- **잎 그늘 아래 친구(`dimmed`):** 그늘에서 조금 어둡게 보이는 필터가 그 친구의 모든 부위 그리기에 걸렸다. 친구를 작은 그림판에 한 번 그리고 같은 비율(×0.86)로 어둡게 겹쳐 붙인다(색은 수학적으로 같음). 엘레판은 잎 우산을 나중에 그리는 구조라 그대로 필터.
- **베이치·코로나(`species-rig.js`):** 팔을 그리려고 매 장 640×640 임시 그림판을 지우고 붙였다(팔 없는 코로나도). 베이치 팔은 몸 뒤라 바로 그리고 몸을 다시 덮는다. 코로나는 건너뛴다.
- **슈퍼범 옆잎(`superbum.js`):** 가만히 서 있거나 쉴 때처럼 조금 흔들리는 옆잎은 흔들림 단계마다 구워 두고(최대 48장), 걷기처럼 크게 움직일 때는 그때그때 휜다.
- **낙엽 자리 그림자:** 흐림 필터를 한 번만 구워 둔다.
- 저장 스키마·규칙 식별자 불변. 버전 1.1.6 / versionCode 82.

측정(크롬 소프트웨어 그리기, 같은 장면):
- 화면 한 장: 기본 화면 약 170ms → 약 15ms, 전체 보기 약 70ms → 약 13ms.
- 부분별(그리기를 그 자리에서 끝내게 해서 잰 값, 기본 화면): 떨어진 낙엽 122 → 0.2ms, 그늘 아래 베이치 54 → 0.4ms, 바위·바위틈·이끼 각 7.4 → 0.7ms, 슈퍼범 6.3 → 2.0ms.
- 휴대폰은 그래픽 칩으로 그려서 숫자가 다르다(필터는 그래픽 칩에서도 비싼 편). Android 실기기 미측정.

화질: 바꾸기 전후 화면을 계절 4개 × 낮·밤 × 기본·전체·확대(25장)로 크롬에서 그려 픽셀 비교. 바뀐 픽셀은 전체의 0~0.2%(구운 그림의 테두리·작은 점무늬, 색값 차이 대부분 50 이하), 확대 화면은 거의 0. 비교 그림 `docs/qa-1.1.6/runtime/before-after.png`.

검증: 렌더 관련 테스트(`render`·`rig`·`ellisii-legacy`·`rock-rider`·`season-landscape`·`selection-ring222`·`young-art`·`inspection`·`superbum`·`stroll`·`lake`), UI, 전체는 CI. `render.test` 가짜 그림판에 임시 그림판·변환 읽기를 더하고, 슈퍼범 옆잎은 구운 그림도 원본에서 나온 것으로 인정하게 고침. Android 실기기 미검증.
